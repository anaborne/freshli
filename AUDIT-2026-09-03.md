# Audit, 3 September 2026

This repository was audited on 3 September 2026 against its own README, its
tests and its CI configuration, by reading every source file and running the
test suite, the typechecker, the linter and the build. Twenty-one issues were
found across two rounds, nine of them in the code written to fix the first
round, and all twenty-one are closed in this commit.

## What changed

### 1. Edit page UPDATE filtered on name alone

The row was fetched with a name and expiration filter and the delete button
filtered on name, unit and expiration, but the update filtered on the name
only. With two batches of the same food under two expirations, saving either
one wrote the same quantity, unit and expiration to both. The update now goes
to the primary key of the row the fetch returned.

### 2. update-inventory keyed inventory by name alone and dropped the parsed unit

The route built a Map keyed on the lowercased name, so a second batch of the
same food overwrote the first and only one row was ever reachable. It also read
the parsed quantity while ignoring the parsed unit, so a line measured in
tablespoons decremented a row stored in pounds. Matching now uses the name and
the unit the parser read, and where several batches match, a new function
`planDeduction` in `lib/ingredients.ts` builds the whole plan before any row is
written, taking the soonest to expire first.

### 3. README claimed all four defects were pinned by a test

Three of the four are pinned. The fourth is a build-config mistake, and the
README's own rule that the suite covers pure functions only rules a test for it
out. The sentence now says three, and names why the fourth has none.

### 4. README described a merge on the photo path that the photo path does not do

The merge-on-match sentence sat under the photo heading, and `confirmUpload`
inserts one row per confirmed item with no lookup. The merge exists on the
manual add form. The README now says where each behaviour lives.

### 5. README and a code comment stated Next 15's config resolution order backwards

Both said Next 15 resolves `next.config.ts` first. In next 15.3.0,
`CONFIG_FILES` is `["next.config.js", "next.config.mjs", "next.config.ts"]` and
the config loader takes the first of those that exists, so the `.js` file wins.
Both places now state that order, which also makes the recorded fix the correct
one.

### 6. Both inventory write paths reported success on a failed write

Neither the manual update, the manual insert nor the photo-path insert checked
the error the Supabase client returns. A rejected write still showed "Saved!"
or "Ingredients added!" and then cleared the form. All three writes are now
checked and return before the success and reset block.

### 7. A failed recipe generation left the page loading for good

`setLoading(true)` ran before the fetch and the error branch returned without
clearing it, and there was no `try`/`finally` around the request. The button is
disabled while loading, so the only recovery was a page reload. The body is now
wrapped in `try`/`finally`.

### 8. README did not say the build needs the three environment values

The OpenAI client is constructed at module scope in two API routes, so Next
instantiates it while collecting page data. With no environment set,
`npm run build` exits 1 at `/api/generate-recipe-image`. The Tests block now
lists `npm run build` with that condition.

### 9. README said CI runs on every push

The workflow is gated to pushes on `main`, and separately runs on every pull
request. The sentence now says so.

### 10 and R2-8. Test timing

"About 150ms" matched neither the wall figure nor the in-test figure. Its
replacement, "well under a second", was also not reproduced on a second
machine. The sentence now reports the figure the repository controls: the
assertions run in tens of milliseconds. Measured here at 20ms to 26ms across
the four CI timezones.

### 11. tsconfig included a file that does not exist, and the Tailwind config was inert

`tsconfig.json` listed `tailwind.config.js`, which is not in the repository, and
the entry is redundant beside `**/*.ts`. It has been dropped. Separately, the
project is on Tailwind v4, which does not load `tailwind.config.ts` without an
`@config` directive, so the `font-rubik` utility applied in `app/layout.tsx`
generated nothing. `styles/globals.css` now carries
`@config "../tailwind.config.ts";`.

### 12. /api/gpt-vision answered 200 for a non-array reply

The route validated that the model's text parsed as JSON and nothing more. A
reply shaped `{ "ingredients": [...] }` parses, and the client maps over what
comes back, so the page threw inside an async handler after the spinner had
already stopped. The route now returns 500 when the parsed value is not an
array.

### R2-1. Float summation invented a shortage

Batches of 0.7 and 0.1 sum to 0.7999999999999999, so a line needing 0.8 was
refused and the raw float was shown to the caller. The comparison now carries a
tolerance of 1e-9 and the reason is rounded to six decimal places.

### R2-2. A batch the planner meant to empty kept a float residue

Batches of 0.1 and 0.2 against a line needing 0.3 left 2.7755575615628914e-17
in the second row, and the route wrote that string to the database. A residue
within 1e-9 of zero is now snapped to zero.

### R2-3. One unreadable quantity blocked every sibling batch

`confirmUpload` can write a blank quantity, so a row that parses as NaN is
reachable. Such a row made the total NaN and refused the whole line. Unreadable
batches are now dropped from the candidate list, and the line is refused only
when no readable batch remains.

### R2-4. A zero-quantity batch produced a pointless UPDATE

A batch holding zero contributed a deduction of zero, which the route wrote back
as "0" over "0". Batches with nothing to give are now skipped.

### R2-5. A negative stored quantity made the planner over-deduct

Batches of -5 and 10 against a line needing 3 raised the negative row to zero
and took 8 from the healthy one. Negative quantities are now treated the same
as unreadable ones and dropped.

### R2-6. A cook that deducted nothing still reported success

The route returned `{ success: true }` unconditionally and the results page
checked only `response.ok`, so a request in which every line was skipped still
sent the user to the dashboard as though the fridge had been updated. The route
now sets `success` from whether any line was applied, and the results page shows
the skipped lines and their reasons before navigating.

### R2-7. Blank-unit and blank-date rows could be updated as a group

The round-1 fix filtered the edit page's update on name, unit and expiration,
which still caught more than one row when two rows shared a blank unit or a
blank date, both of which the photo path can write. The update is now filtered
on the row id from the fetch.

### R2-9. A deletion absent from the repository

The README and the `next.config.ts` comment said "The `.js` file is gone",
describing a deletion that does not appear in the history. `git log --all --
next.config.js` is empty and only `next.config.ts` is tracked. Both places now
say the file was removed before the first commit.

The README's stated test count was raised from 28 to 40 in both places it
appears, and tests were added for R2-1 through R2-5.

## Checked and found correct

Tooling, run on node 22.22.2 after `npm ci` (400 packages):

- `npx tsc --noEmit` exits 0.
- `npm run lint` exits 0 with three `no-img-element` warnings.
- `npm test` reports 40 passed under each of UTC, America/New_York, Asia/Tokyo
  and Pacific/Kiritimati, the four zones in the CI matrix. The count matches the
  two places the README states it. There is no `.skip`, `.only` or `.todo`, and
  every test asserts.
- `npm run build` exits 0 with the three environment values set and emits 13
  routes. With none set it exits 1 while collecting page data for
  `/api/generate-recipe-image`, which is the behaviour the README now records.

Expiry banding. `daysUntilExpiry` floors both sides to local midnight and
rounds, so it does not depend on the time of day and survives a DST transition
between the two dates. The boundaries were checked against an independent
reference that computes the calendar-day difference from local date components:
every day from 1 January 2024 to 31 December 2027, at eight times of day
including 00:30, 01:30, 02:30 and 03:30, against expirations at offsets of -2,
-1, 0, +1, +6, +7, +8 and +9 days. That is 187,008 comparisons per timezone,
run under UTC, America/New_York, Asia/Tokyo, Pacific/Kiritimati,
Australia/Lord_Howe and America/Santiago, for 1,122,048 comparisons with zero
mismatches. In every one of those zones the day of expiry bands as expiring
soon, the day after bands as expired, seven days out bands as expiring soon and
eight days out bands as fresh. The band logic is correct in every timezone the
CI matrix runs.

Secrets. The history is three commits. A scan of every commit for OpenAI-shaped
`sk-` keys, JWT-shaped `eyJ` strings, `service_role`, `AKIA` access-key ids and
private-key blocks returns only the placeholders in `.env.example`
(`https://your-project-ref.supabase.co`, `your-anon-key`, `sk-your-key`). The
only environment file tracked anywhere in history is `.env.example`, and
`.gitignore` covers `.env`, `.env.*` and `.env*.local` with an exception for it.
No secret is committed anywhere in history.

The deduction planner was exercised against the cases most likely to break it.
Fractional quantities that cover (0.7 and 0.1 against 0.8) empty both batches
and report success. Fractional quantities that fall short (0.1 and 0.1 against
0.8) report "needs 0.8, inventory has 0.2". Totals that match the line exactly
empty every batch and leave nothing. A zero batch is left out of the plan, and a
line facing only a zero batch is refused. A negative batch is dropped and the
healthy batch beside it gives up the full amount and no more. String quantities
are read with `parseFloat`, including one carrying a trailing unit. An
unreadable quantity beside a good one is dropped and the good one is spent, and
a line is refused only when no batch is readable. When more batches are
available than the line needs, only the soonest-expiring is touched and the rest
are left alone. A line with no quantity carries no unit, matches on the name
alone and deducts one, which is the documented behaviour. Two lines for the same
food in one request draw from the level the earlier line left behind, and when
the second line then falls short it is reported as skipped while the first
stands as applied.

Also confirmed: `CONFIG_FILES` in the installed next 15.3.0 is
`["next.config.js", "next.config.mjs", "next.config.ts"]`, and resolving that
list against a directory holding all three returns the `.js`. The `.font-rubik`
utility appears in the built CSS, and a control build with the `@config` line
removed does not emit it, so the comment in `styles/globals.css` describes what
happens. The three models named in the README are the three the routes call
(`gpt-4o`, `gpt-3.5-turbo`, `dall-e-2`), and `generateImageWithRetry` does back
off on 429 with three retries and a doubling delay. The prompt asks for nine
recipes. The six categories appear in the stated order with an unrecognised
category falling to miscellaneous. Every path and intra-repo link in the README
resolves. The CI matrix is exactly the four zones named. The MIT licence is
present.

## What remains unverifiable

Everything that needs a live Supabase project or a real OpenAI key was audited
by reading the code. That covers the three OpenAI calls and their failure
paths, the Supabase reads and writes on every page, the row-level security
policies the README asks a deployer to enable, and the column types listed in the
configuration table, all of which were checked by reading the code that assumes
them. The photo path end to end, from an uploaded image through GPT-4o to
confirmed rows, was not exercised. Nor was the loading of a generated image from
the DALL-E host through `next/image`, so the `remotePatterns` entry is confirmed
present and correctly placed but was never observed serving a real URL. The
React components are not covered by the suite and were not rendered. The
attribution in the README's closing line was not checked against any external
record.
